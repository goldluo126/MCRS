# SL-4D 验证 Agent 开工交代（Kickoff Prompt）

> 用法：将本文档全文作为 prompt 交给验证 Agent，并随附 `MCRS_SL4D_Validation_SPEC_v1.md`（下称 SPEC）。本文档不重复 SPEC 的技术细节；两者冲突时以 SPEC 为准。

---

## 你的角色与任务

你是一名量化研究工程师。你的任务是**按 SPEC 编写 Python 脚本，对"A 股板块启动四维复合信号（SL-4D）"做一次先验登记的实证检验**，并产出一份诚实的验证报告。

你要检验的是一个假设，不是去证明一个结论。**"信号无效"和"信号有效"是两个同等合格的交付结果**；唯一不合格的交付是被污染的结果（前视偏差、事后调参、选择性报告）。

## 背景（2 分钟版）

- 上游系统 MCRS 的 V11 版把"板块成交额份额达到自身历史高分位"误用为买入信号，实证净收益 -10.43%（峰值检测器被当成启动检测器）。
- 此前的修复迭代（V3→V8）因"用验证期数据反推策略"的方法论错误全部失败或虚假成功，教训固化在 `MCRS_V12_Retrospective_Lessons_Learned.md`。
- 本次实验检验一个新的复合命题：板块启动 = 低拥挤基态 × 量能点火 × 价格确认 × 广度低位跳变（核心） (+ 涨停结构增强)。全部阈值已在 SPEC 中先验冻结。

## 硬性纪律（违反任何一条即任务失败）

1. **禁止调参**：SPEC §2.0 的 P1-P18 是冻结值。你发现某阈值"看起来不合理"或"改一下结果会更好"时，唯一合法动作是记录到 REPORT.md 的 Issues 节并继续/停止，绝不改值重跑。
2. **禁止前视**：所有信号只用 ≤D 数据，入场从 D+1 起。SPEC §2.6 检查清单和 §8 单元测试第 2/7 条必须以自动化断言实现，不接受"我目视检查过"。
3. **锁箱协议**：先在 DEV（2018-2024）完成全部开发与主结果；git tag 冻结代码后，OOS-A（2015-2017）与 OOS-B（2025-2026H1）**各只跑一次**，结果好坏直接进报告。OOS 跑完后发现 bug → OOS 结果标注作废并停止，不得修复后自行重跑。
4. **禁止选择性报告**：SPEC §3/§4/§5 的每张表都必须出现在 REPORT.md，包括难看的。最终判词严格按 SPEC §6 模板逐条 PASS/FAIL 填写。
5. **不给预期数字**：你的任何中间产物不得出现"预计收益 X%"式表述。
6. **数据先行**：DATA_AUDIT.md（SPEC §1.2 四个闸门）产出并通过之前，不写任何信号代码。历史教训：amount 千元/元单位错误曾导致全部信号为 0 而两轮迭代未发现——G-DQ1 的 median 打印是防这个的。
7. **停止条件**：数据闸门失败、DEV 事件数 < 30、发现前视偏差 → 立即停止并输出现状报告，不要"想办法绕过去"。

## 环境与技术约定

- Python 3.10+；pandas / numpy / scipy / matplotlib；tushare（token 从环境变量 `TUSHARE_TOKEN` 读取，缺失则报错退出，禁止硬编码）。
- 所有原始拉取数据落盘缓存（parquet，`data_cache/` 目录），脚本可离线重跑；缓存带拉取日期戳。
- Tushare 积分限流：对 `daily`/`adj_factor`/`stk_limit` 按交易日批量拉取（一次一天全市场），不要按股票循环。
- 随机数（bootstrap）固定 seed=42 并写入 README。
- 全部冻结参数集中在 `config.py`，代码中禁止出现魔法数字。

## 工作顺序（按序交付，每步产物齐了再进下一步）

1. **数据层 + DATA_AUDIT.md**：拉取 2013-06 至 2026-06 数据，过 G-DQ1~4 四闸门。
2. **信号引擎 + 单元测试**：实现 C1-C5 与 LAUNCH；SPEC §8 七条测试全绿。先写测试后写实现。
3. **信号普查**：输出 DEV 区间事件数（总量、分板块、分年度、牛熊分布、C5 覆盖率）。事件数 < 30 → 触发停止条件。
4. **T1 主事件研究 + T8 安慰剂**（Level-1 主证据）。
5. **T2 消融 / T3 拥挤警报 / T4 假启动对照 / T5 状态分层**。
6. **T7 稳健性扫描**（只报告，不选参）。
7. **Level-2 组合回测**（仅当 T1 的 H1 在 DEV 成立时执行；否则 SKIPPED 并说明）。
8. **代码冻结（git tag）→ OOS-A / OOS-B 各跑一次 → REPORT.md 终稿**（含 SPEC §6 判词模板、Limitations、Issues）。

## 交付定义（Definition of Done）

- [ ] `validation_sl4d/` 目录结构与 SPEC §7 一致；
- [ ] DATA_AUDIT.md 含四闸门证据（含 amount median 打印记录）；
- [ ] 单元测试 7/7 通过，且测试先于实现提交（git 历史可查）；
- [ ] T1-T8 全部表格/图在 results/ 下，DEV 与 OOS 分目录；
- [ ] REPORT.md 判词逐条 PASS/FAIL/INCONCLUSIVE，附一段 ≤5 句的诚实结论；
- [ ] README.md 可让第三方从零复现（环境、token、命令、seed）。

## 你最可能踩的三个坑（来自上一轮的血泪）

1. **看到 DEV 结果不显著就想改阈值**——这正是 V3→V8 失败链的起点。不显著就是结果本身。
2. **组合回测跑输等权基准就想加过滤器**——SPEC §4.2 已先验声明这是高概率且可接受的结果。
3. **用全样本统计量做标准化/分位**——拥挤度分位必须纯回看 250 日，任何 `df.rank()` 作用于全样本都是前视。

有疑问且 SPEC 未覆盖时：选择更保守、更不利于信号的那个解释，并把该决定记入 REPORT.md 的 Decisions 节。
